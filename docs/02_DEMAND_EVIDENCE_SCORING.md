# 《真需求》方法论工程化：证据、反证、付费推断与评级引擎

> 版本：Methodology 0.1.0（可替换、可回滚，非梁宁原书评分公式）\
> 资料出处：梁宁《真需求》，用户上传 MD/PDF；页码均指书本印刷页码（可能与 PDF 物理页码不同）。\
> 原书理念与本产品派生规则严格区分：`BOOK` = 原书概念提炼；`DESIGN` = 我们的工程方案；`HYPOTHESIS` = 需要市场验证的商业假设。

## 1. 原书理论的准确映射

### 1.1 主轴不是单一需求强弱，而是商业闭环

| 原书内容 | 阅读定位 | 工程翻译 | 预防的误判 |
|---|---|---|---|
| 价值—共识—模式商业闭环 | 序，1–7页 | 三级分析中必须分别保存 `value_review`、`consensus_review`、`model_review` | 有价值却无法成交、能成交却无法生存 |
| 产品价值 = 功能 + 情绪 + 资产 | 第一部分，6–7页、69–77页 | `value_mix` 三维，按用户场景解释，不是简单相加的数值公式 | 只观察功能或价格 |
| 功能价值核心：基础/效率需求 | 第1章，9–29页 | 当前流程的时间/成本/安全/可靠性 + 新方案改善量；兼顾供应链/IP/基础设施 | 工具产品没有结构性优势 |
| 情绪价值：生理唤起、认知标记、心理账户；保障感/愉悦感/彰显性 | 第2章，31–51页 | 识别客户真正购买的情绪结果及可观测的行为，支付者的心理账户必须匹配 | 将热点话题当成购买意愿 |
| 资产价值依赖可持续变现的市场与共识 | 第3章，53–67页 | 资产/收藏/转售类产品额外检查流动性、产权/交易渠道和共识稳固性 | 把故事性稀缺当可兑现资产 |
| KANO：必备/期望/魅力/无差异/反向 | 第6章，199–210页 | 分用户、分场景归类产品特性与用户感知 | 产品做了很多功能，用户并不买单 |
| 用户画像 ≠ 用户人设 | 第7章，211–228页 | 人口属性仅做样本标签，人设/身份目标用于解释主动投资与弹性需求 | 不缺≠需要；越擅长越愿继续投入 |
| 场景穷举与识别、产品场景匹配 | 第8章，229–244页 | 事件触发、频次、角色、地点、当前行为、替代路径的场景结构化 | 脱离具体情景谈抽象痛点 |
| 利益相关人地图；共识成果是成交与关系 | 第9–11章，245–299页 | 区分购买者、使用者、预算持有人、审批者、利益受损方 | 用户喜欢但组织不采购 |
| 模式：能力系统、变现逻辑、分配机制；「拿谁的钱」 | 第12–14章，337–404页 | 区分 To C / To B / To VC / To G；资金来源、持续收入、组织/供应链控制能力 | 市场有需求但自己没赚钱模式 |
| 应然与实然、行动力和第一性原理 | 第15–16章，421–441页 | 反事实、最小可观察行动、品类根本目的、不能只靠想象推导 | 把「应该如此」写成「已发生」 |

### 1.2 原书思想的三个特别容易误读之处

1. 书中「付费决定商业价值」是从**买方及交易视角**审视商业，不等于「拿不到付费数据→需求不存在」；本系统允许继续研究，但不能给已验证成交的结论。
2. 情绪价值不等于社交媒体热度；心理账户、感知和能够交付的体验才是关键。对情绪型机会不能强制用 B2B 效率 ROI 替代其评价标准。
3. 模式不只是定价/营收。即使一个需求已有真实交易，也要核查组织所具备的**交付、供应链、获客、交易控制与资源再投入能力**。

## 2. 核心研究序列（每一步输出结构化对象）

```text
Signal -> normalize -> EvidenceCluster
       -> Who/When/Where/Job/Cost/Workaround 需求识别
       -> VALUE: 功能/情绪/资产，当前与目标价值差
       -> CONSENSUS: 感知属性/KANO/人设/场景/利益相关人/购买阻力
       -> MODEL: 谁付钱/资金路径/单位经济/复购/能力系统/分配
       -> COMPETITION: 直竞/间竞/替代/非消费/市场进入
       -> CONTRADICTION: 反证、空白、相反解释、关键假设
       -> EVIDENCE GRADE + SCORE + UNCERTAINTY
       -> DECISION: 深挖/实验/观察/否决/暂不判断
       -> 研究版本冻结 + 后续重评触发
```

同一问题最多存在多种合理产品方案，**Need 不依赖 Opportunity 才存在**。AI 不得直接把「我想做一个 App」当成已验证需求。

## 3. 「缺少直接付费证据」的正式解法

### 3.1 付款与受益者图谱：先问钱从哪里来

针对每个机会，分别填充：

- **User**：谁使用/体验产品；**Beneficiary**：谁从结果中受益。
- **Payer**：实际付款主体；**Budget owner**：谁控制预算；**Decision maker**：谁批准交易；**Influencer/Blocker**：谁推动/阻碍。
- **Revenue path**：用户直接支付、企业采购、广告/赞助、商家交易抽成、授权/IP、政府采购、基金/资本补助等，需注明「可持续经营」与「资金筹措」差异。融资（To VC）不能自动当经营性收入。

当找不到用户付费数据时，可能只是研究错了付款人。先识别商业结构再判断 WTP。

### 3.2 付费证据等级（本产品设计规则；不是作者原书等级）

| 等级 | 可用证据 | 可推断的最强结论 | 禁止推断 |
|---|---|---|---|
| L0 未知 | 仅热度、口号或无可靠数据 | 存在话题/线索 | 有真实痛点、有人愿付费 |
| L1 需求行动 | 用户反复求助、尝试替代方案、明确投入时间 | 问题可能具有行为强度 | 会购买本产品 |
| L2 购买意向 | 合格询价、索取报价、预约产品演示、进入采购流程 | 存在具体购买兴趣 | 成交率/营收已成立 |
| L3 现有替代付费 | 目标用户正在为人力、工具、外包或替代产品支付成本，记录来源和可比性 | 有可观察的付费预算或成本承受能力 | 本产品必获同等预算 |
| L4 同细分市场交易 | 可信的同类竞品成交、企业采购、合同、持续订阅的公开证据 | 类似客群已有已实现市场交易 | 新进入者能获客/盈利 |
| L5 目标方案真实支付 | 自身预售/订单、实际回款、续费/复购实验经核实，注明样本和时段 | 特定客群已为具体价值主张付费 | 已有规模化利润、普适成功 |

**不机械排序**：L2 可能出现在 L3 之前/之后；记录类型 `evidence_type`，等级仅用于沟通强度，不能掩盖样本匹配性、付款身份或观察跨度。没有实际购买数据时可停留在 L0–L3，继续研究机会本身。

### 3.3 可观测的代理变量

| 代理证据 | 计算方式 | 核心陷阱 | 推荐下一步 |
|---|---|---|---|
| 现有人工耗时 | 频次×每次分钟×相关职位全成本（口径分层） | 时间价值未必形成现金预算 | 访谈确认可释放预算与流程 |
| 重复返工/错误损失 | 事件数×可量化损失 × 可避免比例 | 损失样本非代表总体 | 使用真实历史案例核对 |
| 替代服务支出 | 发票/公开报价/采访中可核实的现有金额 | 销售价格与成交价格不同 | 确认目标用户是否正在支付 |
| 竞品公开定价 | 套餐×购买单位（仅当买家数有独立证据） | 不能由网站价格推算收入 | 寻找真实客户评论、合同 |
| 招聘/新岗位 | 招聘量、薪酬区间、职责、公司数量 | 招聘并非软件采购意向 | 研究可替代流程与采购负责人 |
| 采购/招标文件 | 采购预算、公告、合同、验收条款 | 单次项目不代表长期市场 | 研究采购周期、资质与集中度 |
| 主动询价、排队、等候名单 | 按真实用户/企业去重、实际后续动作 | waitlist 不等于付费 | 预约付费试点、预售（经批准） |

### 3.4 推断输出规范：不能把「成本节省」直接当「愿付价格」

```yaml
payment_assessment:
  payer_persona: 企业财务负责人
  payment_stage: L1
  direct_payment_verified: false
  evidence_items: [EV-101, EV-138]
  proxy_metrics:
    - name: monthly_manual_hours
      value_range: [20, 70]
      unit: hours_per_team_month
      source: user_interview_sample
      status: estimated
  candidate_benefit: "减少人工对账时长（未实测）"
  estimated_willingness_to_pay: null
  key_unknowns:
    - 预算控制人是否愿意从人力成本转换为软件订阅
    - 现有 ERP 是否已覆盖主要流程
  next_cheapest_test:
    action: 访谈 8 位具有采购权限的目标客户并做真实报价测试
    approval_needed: true
  conclusion: 潜在价值值得进一步验证，付费意愿尚未证实
```

算法不得默认使用 `工时成本 × 30%` 之类无依据的付费比例。必要时仅给条件区间：**在 A、B、C 假设成立时，单位经济模型可达 X–Y**，标注情景而非预测事实。

## 4. 三种本质不同的评分

### 4.1 商业潜力评分 `opportunity_potential_score`

**默认研究权重（拟议，不是梁宁原书）**：

| 维度 | 权重 | 子项与证据 |
|---|---:|---|
| V 需求与价值强度 | 25 | 场景/频次、伤害/收益量级、已采取行动、功能/情绪/资产价值 |
| P 产品方案与价值差 | 20 | 对现有方式改善、差异化、可交付性、KANO与场景适配 |
| C 共识与交易阻力 | 15 | 感知、心理账户、购买链路、利益相关人、使用习惯变更阻力 |
| M 模式与可持续性 | 20 | 谁付钱、收入路径、单位经济、复购/持续需求、组织能力 |
| E 市场进入吸引力 | 20 | 竞品强度、替代、获客渠道、监管/供应链壁垒、切入窗口 |
| **合计** | **100** | **仅在证据覆盖达标时展示点估值** |

每项子因子范围 0–1，取加权均值再映射 0–100；所有因子需保存证据、缺失与权重。**未知(null) ≠ 0 分**。

**可信度约束**：
- 核心维度数据覆盖率 `<60%`：总分 `null`、等级 `UNRATED`；显示分维度已知情况与「下一步搜证」。
- 覆盖率 `60%–79%`：仅可发布**区间 + 低/中置信提示**，不可在公榜作为已确认 S/A。
- 覆盖率 `≥80%` 且无高影响冲突：可发布点分与区间，前端同时展示独立证据可信度。
- 任一关键维度遇到高可信反证，进入 `manual_review` 或 `red_flag` 状态，不让其他高分抵消红线。

### 4.2 决策等级 `readiness`

这是另一轴，不等于潜力分：

| 等级 | 定义 | 允许行动 |
|---|---|---|
| R0 情报线索 | 仅有提示，关键证据不足 | 补证据 |
| R1 需求可疑/待澄清 | 已有一定问题行为，但尚未明确受益主体 | 访谈/跟踪 |
| R2 需求值得验证 | 痛点与客群较明确，付费或交易路径未验证 | 低成本实验 |
| R3 模式初证 | 有可核实的购买/合作或强代理证据，能描述商业闭环 | 小规模试点 |
| R4 入场候选 | 商业与交付约束均通过阶段门，差异化成立 | 审核立项 |
| R5 实际运营验证 | 真实 MVP/商业化数据支持一部分结论 | 扩量/重新优化 |

「R4」不是建议所有用户马上投入。还需独立展示可行性、资源适配与风险。

### 4.3 证据可信度 `evidence_confidence`

建议由以下独立变量组成（可评估/校准）：
- **直接性**：是否观察真实行为/交易，而非口头意愿；
- **独立性**：不同原始数据簇，而非转载；
- **可审计性**：原链接、时间戳、官方记录与出处；
- **新鲜度**：与该市场变化速度相比是否过时；
- **代表性**：细分用户/地区/时间是否相近；
- **冲突与偏差**：是否反常、广告/水军、平台采样偏差、缺失大量反例。

计算不宜以来源数线性相加。建议在前 30 个标注案例上调整 `confidence_model_version`。**可信度是证据质地，不是市场机会大小**。

### 4.4 市场进入难度与用户适配

`execution_difficulty` = 技术/资金/合规/组织/周期/供应链瓶颈，不因机会上佳就自动较低。`personal_fit` = 用户技能/时间/资金/渠道/团队/地域/行业经验；用户不提供资源时显示 `not_personalized`，不擅自推断。

### 4.5 潜力评级 S/A/B/C/D 映射（仅经证据门槛）

建议初始阈值：S≥85、A70–84、B55–69、C40–54、D<40。**这些阈值只是 UI 初始值**；不可跨行业当作天然客观尺；必须在每个垂直行业和地区验证，并允许通过后台版本化修改。低可信但高潜力项目标为 `potential_band=S; readiness=R2; confidence=LOW`，**不标「已验证 S 级」**。

## 5. 反证与否决系统

**每个商业结论都必须同时生成竞争解释**：

- 假设「市场上没人做 → 蓝海」→ 反证「没人付钱 / 合规无法满足 / 创造成本大于价值」。
- 假设「大家抱怨 → 必定愿买」→ 反证「当前免费替代已足够 / 用户只愿付出注意力」。
- 假设「竞品贵 → 我们便宜就能赢」→ 反证「获客或履约成本高 / 品牌保障难替代」。
- 假设「国外已验证 → 国内可复制」→ 反证「支付习惯、监管、渠道、文化、采购权不同」。
- 假设「技术可以做 → 能交付」→ 反证「产能、牌照、组织能力、长周期运维缺位」。

**否决记录**应有 `condition`, `evidence_ids`, `severity`, `reviewer`, `recheck_trigger`, `effective_from`, `reversal_history`。有效监管红线可暂停推荐；资料不足只能进「暂无法判断」，不能直接写失败。

## 6. 不同商机的最低成本验证实验建议

| 商机 | 首先确认什么 | 优先实验 | 记录的行为证据 |
|---|---|---|---|
| B2B 效率软件 | 预算人/流程损失/采购阻力 | 买方访谈、报价演示、5 客户意向协议 | 回复、带预算的试点意向、签约/付款 |
| 消费情绪型 | 是否有心理账户、是否重复购买 | 展示可交付体验样本、受控预售 | 实际购买、复购、主动分享与口碑 |
| 硬件实物 | 核心功能和交付能力 | 预约试用、成本核算、小批原型 | 定金、可接受价格、退货原因 |
| 本地服务 | 区域场景、时段、服务密度 | 小范围人工履约试点 | 到店/复购/履约成本 |
| 企业基础设施 | 切换成本/稳定性/采购周期 | 沙盒集成、合规评审、试点合同 | 需求评审通过、POC 结果、采购进展 |
| 双边市场 | 两侧是否可同时形成密度 | 小区域两侧招募、手工撮合 | 交易匹配率、履约率、抽佣可持续性 |
| 未来潜力 | 哪个触发条件会启动需求 | 定期监控技术/政策/习惯转折 | 触发事件、付费行为变化 |

**实验状态机**：`draft -> awaiting_approval -> running -> completed / canceled -> reviewed`。只允许用户上传或经授权接口返回的真实结果成为 `observed_outcome`。

## 7. 多模型交叉验证：权重从哪里来

```text
Model A：需求主张 + 证据摘要 + 结构化结论
Model B：反证挑战（独立推理，优先不同供应商）
Verifier：仅基于 EvidenceID 检查事实/引用、数值与出处
Evaluator：按 MethodologyVersion 评分和给研究动作
Human：审定争议、高影响风险及终止/批准
```

只允许 `Verifier` 从已有证据认定 `confirmed_fact`。模型都同意而证据不足时仍为 `inference`。

## 8. 方法论 Skill 划分与发布规范

| Skill ID | 核心输入 | 核心输出 | 原书/派生 |
|---|---|---|---|
| `need-discovery` | Signal 集合 | Persona/Scenario/Job/Need | DESIGN，原书场景方法启发 |
| `value-audit` | Need + 候选产品 | 功能/情绪/资产及价值差 | BOOK→DESIGN |
| `kano-perception` | 产品特性与客户证据 | 五类属性及争议 | BOOK→DESIGN |
| `consensus-map` | Stakeholders + 旅程 | 利益分歧、认知阻碍、触点 | BOOK→DESIGN |
| `business-model-audit` | payer/渠道/成本/收入 | 能力/变现/分配 | BOOK→DESIGN |
| `payment-proxy` | 替代支出等 | L0-L5、事实/假设、最小实验 | DESIGN |
| `competitor-map` | Need/Market | 直接/间接/替代 + 缺口 | DESIGN |
| `counter-evidence` | 主张/支持材料 | 反证、否决条件、反事实 | DESIGN，原书求真启发 |
| `entry-decision` | 所有审计及角色约束 | 独立评分/分流/建议 | DESIGN |
| `experiment-designer` | 证据缺口/预算 | 实验、门槛、记录模板 | DESIGN |

Skill 发布必须存 `id, semver, prompt_digest, input_schema, output_schema, allowed_tools, allowed_sources, evaluator_set, approval_policy, owner, changelog`。更新先跑旧/新对照 30 个样本再灰度，保留可回滚版本。

## 9. 案例评估：模拟数据，不能冒充真实发现

**案例**：「中小企业跨系统应收对账」——纯模拟，用于测试产品正确性。

输入：10 条用户抱怨、4 条重复转载、1 篇竞争者官网定价，缺乏真实销售数据。系统应：
1. 原始 10+4 条不直接变成 14 个独立用户证据；记录重复簇。
2. 按企业规模、会计场景、系统组合拆分为不同子需求。
3. 标记功能价值 = 时间/错误率改善的**假设**；情绪价值 = 保障感（审计/不出错），但需证据。
4. 付款人可能是财务负责人或企业采购；必须查预算/审批权。
5. 在付款不明时，不填 WTP 金额；提出约见买方并做报价测试。
6. 竞品既有 SaaS、ERP 自带模块，也有 Excel + 人工对账。
7. 机会可以评估为高潜力但 `R1/R2`，不能标为「已验证付费」。

## 10. 校准评估集设计

必须有**正例、反例、边界案例、反事实、不同市场案例**；每例至少提供：原始证据集、人工标注的 claim 类型、支持/反证、付款人、用户场景、合理等级区间、应该拒绝的结论。初始样本矩阵 30–60 个：
- 10 个真实但难赚钱；10 个竞争多但可差异化；10 个热度高无行为；
- 10 个付费数据缺失但存在替代支付；5 个跨市场复制失败；5 个买方与使用者分离。

核心指标：证据支撑率、无来源断言率（关键事实零容忍）、抽样独立性、需求边界准确度、错误否决率、评分稳定性、跨市场偏差、研究成本、用户完成实际验证率。
